# 团队代码审查标准与流程（Code Review 规范 v1.0）

> 制定人：代码审查专家（火眼眼） · 适用：乙方团队全部代码交付（技能包 / 原型 / 脚本 / 配置）
> 版本：v1.0（2026-08-14） · 状态：待全员评审通过后执行

---

## 0. 这份规范解决什么问题

团队代码质量参差不齐的根因，通常不是"写代码的人能力差"，而是：

| 症状 | 根因 | 本规范的对应章节 |
|------|------|-----------------|
| 同一个坑反复踩 | 经验没沉淀成标准 | §3 审查清单 + §9 案例库 |
| 审查流于形式（"没问题，合并吧"） | 没有分级标准，不敢/不会提意见 | §2 问题分级 + §5 评论规范 |
| 审查拖 3 天没人看 | 没有流程和时限 | §4 审查流程 |
| 安全漏洞上线才发现 | 没有安全检查项 | §3.2 安全清单 |
| 各写各的，风格分裂 | 没有一致性检查项 | §3.3 可维护性清单 |

**一句话定位**：代码审查不是"找茬"，是团队的质量闸门 + 知识传递通道——每个评论都要让别人变强，不是让别人难受。

---

## 1. 审查总则（六条）

1. **具体化**：评论必须落到"文件:行号 + 现象 + 根因"，禁止"这里有问题"式的空话。
2. **说原因**：每条建议必须解释 Why——"为什么这是问题、为什么这么改"，否则对方学不到。
3. **分级处置**：🔴 阻塞合并 / 🟡 建议修改 / 💭 可选优化 / ✅ 明确表扬——不把风格偏好当阻塞项。
4. **及时响应**：审查者 24h 内给反馈；作者 24h 内回应（同意/解释/反驳都行，不能沉默）。
5. **双向学习**：审查者要理解作者的上下文（赶工/兼容性约束/历史包袱），作者要虚心接受建设性意见；被驳回的评论是双方学习的机会。
6. **建设性语气**：对代码不对人；用"考虑 X 因为 Y"而不是"你写错了"。

## 2. 问题分级标准

| 级别 | 标记 | 定义 | 处置 |
|------|------|------|------|
| **Blocker** | 🔴 | 必须修复才能合并：安全漏洞、数据丢失/损坏风险、崩溃/死锁、破坏已有契约（API 格式/文件格式/兼容性）、关键路径无错误处理、**未申报的妥协/技术债**（见 §3.6） | 合并前必须解决；解决后需复审确认 |
| **Suggestion** | 🟡 | 应该修复但不阻塞：缺输入校验、命名混乱/逻辑难懂、重要路径缺测试、明显性能问题、可提取的重复代码 | 作者应修复；确实不改需在 PR 里说明理由 |
| **Nit** | 💭 | 可选优化：风格不一致（无 linter 覆盖时）、命名微调、文档补充、另一种更优雅的实现 | 随手改或记入 backlog，不阻塞 |
| **Praise** | ✅ | 值得表扬：巧妙的设计、干净的抽象、覆盖到位的测试、主动处理的边界情况 | **必须表扬**——这是知识传递和士气来源，每个 PR 至少找 1 处 |

**判定铁律**：
- 不确定是否 Blocker → 按 Blocker 提出，由维护者裁决（§4.4）；
- 纯个人风格偏好（缩进/引号/换行）→ 一律 Nit，且优先交给 linter 而不是人；
- 每个 PR 必须有 ✅ 表扬——只挑毛病不表扬的审查，没人愿意听。

## 3. 审查清单（Checklist）

> 审查者按此清单逐项过；打钩后把结论写进 PR 评论。**清单不是摆设，是审查的"不遗漏保障"。**

### 3.1 正确性（🔴 为主）

| # | 检查项 | 严重级 |
|---|--------|--------|
| C1 | 逻辑是否符合需求描述？有没有"实现了一个功能，但和需求不是一回事"？ | 🔴 |
| C2 | 边界情况：空输入 / 0 值 / 负数 / 超长文本 / 重复提交 / 并发调用 | 🔴 |
| C3 | 状态变更是否幂等？重复执行同一操作结果是否一致？ | 🔴 |
| C4 | 错误路径：try/catch 是否覆盖了所有可失败点（文件 IO、网络、解析）？失败后状态是否回滚？ | 🔴 |
| C5 | 数据一致性：有没有**同一份数据两处维护**（违反单一数据源原则）？ | 🔴 |
| C6 | 日期/时间/时区/编码处理是否正确（如 Windows 下 emoji/中文编码、路径分隔符）？ | 🟡 |
| C7 | 异步：有没有竞态（先发的请求后到覆盖结果）、未 await 的 Promise、事件监听泄漏？ | 🔴 |

### 3.2 安全性（🔴 为主，出问题代价最大）

| # | 检查项 | 严重级 |
|---|--------|--------|
| S1 | **路径安全**：用户输入拼接文件路径是否有 `../` 路径穿越？是否有黑/白名单校验？ | 🔴 |
| S2 | **敏感文件**：是否可能暴露配置/密钥（如 `llm.config.json`、`.env`、`.git`）？**静态资源目录必须有黑名单** | 🔴 |
| S3 | **注入**：SQL 拼接 / Shell 拼接 / 模板字符串拼接用户输入（XSS）？优先参数化/转义 | 🔴 |
| S4 | 输出转义：渲染到 HTML/SVG 的内容是否做了 `& < >` 转义（防止 SVG 注入）？ | 🔴 |
| S5 | 输入校验：所有外部输入（请求参数、文件内容、CLI 参数）是否校验格式和范围？ | 🟡 |
| S6 | 认证/授权：敏感操作（写、删、保存）是否有权限检查？ | 🔴 |
| S7 | 密钥硬编码：代码/仓库里有没有明文密钥、token、密码？ | 🔴 |

### 3.3 可维护性（🟡 为主）

| # | 检查项 | 严重级 |
|---|--------|--------|
| M1 | 命名：变量/函数/文件是否**见名知义**（`data`/`temp`/`x` 类命名要警惕）？ | 🟡 |
| M2 | 单一职责：函数/组件是否只做一件事？超过 60 行的函数是否该拆？ | 🟡 |
| M3 | DRY：有没有 3 处以上重复且可提取的代码？**注意：过度抽象也是债**，2 处重复先不抽 | 🟡 |
| M4 | 注释：复杂逻辑（正则/算法/魔法数字）有没有"为什么这么做"的注释？注释是否与代码同步？ | 🟡 |
| M5 | 死代码：有没有未使用的变量/函数/文件/依赖？ | 🟡 |
| M6 | 结构：文件边界是否清晰？模块间依赖是否单向、无循环？ | 🟡 |
| M7 | 兼容性：改动是否破坏已有调用方（函数签名/文件格式/API 契约）？ | 🔴 |

### 3.4 性能（🟡 为主）

| # | 检查项 | 严重级 |
|---|--------|--------|
| P1 | 循环内做 IO/重计算（循环内读文件、发请求、重复 JSON 解析）？ | 🟡 |
| P2 | 大数据量下的复杂度陷阱：O(n²) 双重循环、全量重渲染、未去重的 find-in-loop | 🟡 |
| P3 | 前端：频繁 innerHTML 全量重建（交互卡顿元凶）、事件重复绑定、无防抖的 input 监听 | 🟡 |
| P4 | 是否真的需要优化？**先度量再优化**——无数据支撑的"优化"可能引入复杂度和 bug | 💭 |
| P5 | 资源释放：长连接/定时器/文件句柄是否及时释放？ | 🟡 |

### 3.5 测试（🟡 为主）

| # | 检查项 | 严重级 |
|---|--------|--------|
| T1 | 本次改动对应的测试是否覆盖：主路径 + 至少 1 个边界 + 至少 1 个错误路径？ | 🟡 |
| T2 | 是否包含**回归测试**（针对已修 bug 的用例，防止复发）？ | 🟡 |
| T3 | 测试是否真实有效？**模拟/假事件是否可能假阳性**（§9 案例4：dispatchEvent 通过但真实鼠标失败）？ | 🔴 |
| T4 | 测试数据是否写死环境相关路径（如 `/tmp`、绝对路径、本机用户名）？ | 🟡 |
| T5 | CI 是否在跑测试？改动是否让 CI 全绿？ | 🔴 |

### 3.6 工程治理（团队特色，🔴 对齐既定原则）

| # | 检查项 | 严重级 |
|---|--------|--------|
| G1 | **零技术债**：有没有"先用着后面再重构"式的妥协（最小可用版/临时方案/复制粘贴改造）？ | 🔴 |
| G2 | **妥协申报**：确需妥协的，是否已明确告知用户 + 写入 `compromise-register.md`？**未经申报的妥协=违规** | 🔴 |
| G3 | **单一数据源**：产出与管理系统是否读同一份数据？有没有数据分叉？ | 🔴 |
| G4 | 架构一致性：改动是否符合既定架构（如画布编辑器=浏览器 ESM 复用现有模块），有没有引入架构分叉？ | 🔴 |
| G5 | 文档同步：改动涉及的文档（规格/SKILL.md/手册）是否同步更新？ | 🟡 |

## 4. 审查流程

### 4.1 角色与职责

| 角色 | 职责 | 要求 |
|------|------|------|
| **作者** | 提交 PR、自检、响应评论、修复 | 提交前必须过 §4.0 自检清单 |
| **审查者** | 按 §3 清单逐项审查、给分级评论 | 由**非作者本人**担任；核心模块须 2 人 |
| **维护者** | 裁决争议、最终合并 | 有 Blocker 未解决时禁止合并 |
| **代码审查专家（AI）** | 兜底审查、案例库维护、新人带教 | 可随时发起，不替代人工审查 |

### 4.2 流程步骤（8 步闭环）

```
① 自检    作者：过自检清单（§4.0）→ 本地单测全绿 → 提交 PR
   ↓
② 提交    PR 描述按模板（§6.1）填写：改了什么/为什么/怎么测
   ↓
③ 分配    维护者：24h 内分配审查者（核心模块 2 人）
   ↓
④ 审查    审查者：按 §3 清单逐项过 → 分级评论（🔴🟡💭✅）
   ↓
⑤ 反馈    审查者一次性给全（禁止挤牙膏式追加）+ 明确"合并条件"
   ↓
⑥ 修复    作者：24h 内回应每条评论（修复/解释/反驳）；🔴 必须修
   ↓
⑦ 复审    审查者确认 🔴 已解决 → 可请求 AI 兜底复审
   ↓
⑧ 合并    维护者：🔴 清零 + CI 绿 → 合并；合并后写复盘备注
```

### 4.3 时限要求

| 环节 | 时限 | 超时处理 |
|------|------|---------|
| 分配审查者 | 提交后 24h 内 | 维护者指定或轮值表兜底 |
| 首轮反馈 | 分配后 24h 内 | 提醒；再超时由维护者接管 |
| 作者回应 | 收到评论 24h 内 | 提醒；Blocker 未回应超 48h 可打回 |
| 合并 | 🔴 清零 + CI 绿 | 立即合并，不积压 |

**小改动豁免**：单文件 < 50 行且不影响现有逻辑的修改（文档、注释、配置），可由作者自审 + 维护者快速复核，不走全流程。

### 4.4 异常处理

| 场景 | 处置 |
|------|------|
| **争议**（作者认为评论不合理） | 双方各说明理由 → 维护者裁决 → 裁决结果记入 PR 评论，作为后续判例 |
| **紧急修复**（线上故障） | 可先合并后补审（24h 内补），**但必须事后补完整审查记录**，禁止借"紧急"绕流程 |
| **大改动**（架构级，>500 行或涉及架构调整） | 升级为**设计评审会**（§4.5），先评方案再写代码 |
| **新人代码** | 审查者增加带教模式：每条评论附"为什么"，必要时安排结对 |

### 4.5 架构级改动：先设计评审，再写代码

架构调整（框架选型、模块拆分、数据模型变更）**禁止直接进 PR**：

1. 作者写**设计文档**（背景/方案/备选方案对比/影响面/风险）
2. 维护者 + 审查者 + AI 三方评审，达成一致
3. 评审通过才允许写代码 → 代码走正常审查流程

> 对应团队原则：**零技术债**——架构决策一次做对，评审是防止"先干起来再说"的唯一闸门。

## 5. 评论规范

### 5.1 评论格式模板

```
[级别] [类别：主题]
文件:行号：<具体问题描述>

**为什么：** <根因/影响/会引发什么后果>

**建议：**
- <方案1>
- <方案2（可选）>
```

### 5.2 示例

```
🔴 **Security: 路径穿越**
preview-server.mjs:312：文件名直接拼进 path.join(DIR, name)，未校验。

**为什么：** 攻击者传 `../../llm.config.json` 可读取 API 密钥（团队真实踩过）。

**建议：**
- 加敏感文件黑名单（llm.config.json/.env/.git → 403）
- 用 path.resolve 后校验是否仍在 DIR 内
```

```
✅ **Praise: 测试意识**
test-core.mjs:188：给 END 关键字 bug 加了回归用例——这类"修完就忘"的 bug 最容易复发，锁死它很专业。
```

### 5.3 反模式（审查者禁止）

| 反模式 | 为什么禁止 | 替代 |
|--------|-----------|------|
| 只给"👍/LGTM"没有具体评论 | 等于没审 | 至少列 1 条具体观察 + 1 条表扬 |
| 挤牙膏式追加评论（审一半发一半） | 打断作者节奏 | 一次性给全，想到再补发并说明 |
| 用风格偏好阻塞合并（"必须用单引号"） | 消耗信任，无质量收益 | 交给 linter；人只审逻辑 |
| 只批评不表扬 | 打击士气，没人愿意被审 | 强制 ✅ ≥1 |
| 评论不落到行号 | 对方找不到 | 评论必须带 文件:行号 |

| 字段 | 内容 |
|------|------|
| PR 号 / 标题 | |
| 作者 / 审查者 / 维护者 | |
| 审查耗时（人·小时） | |
| 问题数：🔴 / 🟡 / 💭 / ✅ | |
| 关键问题摘要 | |
| 是否触发案例库更新 | |
| 复盘备注（下次怎么更快） | |

### 6.3 自检清单（作者提交前过一遍，贴在 PR 描述里）

```
□ 本地单测全绿（node --test）

□ 改动涉及文档已同步
□ 兼容性：未破坏现有调用方
□ 至少 1 个边界 + 1 个错误路径已测
```

## 7. 自动化辅助（人审之前，机器先拦）

> 目标是：**机器能查的绝不浪费人**。人工审查聚焦逻辑/设计/安全语义，机械问题交给 CI。

| 层级 | 工具 | 拦截内容 | 现状 |
|------|------|---------|------|
| L1 语法 | `node --check` / linter | 语法错误、明显风格 | ✅ 已有 |
| L2 单测 | `node --test` | 逻辑回归 | ✅ 15/15 |
| L3 验收 | `agent-batch --dir templates` | 批量功能验收 | ✅ 100 模板 |
| L4 冒烟 | 模板匹配/渲染冒烟 | 关键路径可用 | ✅ 已有 |
| L5 安全检查 | **建议新增**：`scripts/check-secrets.mjs` | 提交前扫描：`llm.config.json`/`.env`/`api_key=`/`password=`/内网 IP | ⚠️ 待做 |
| L6 审查门槛 | **建议新增**：PR 模板校验 + 🔴 未清零禁止合并 | 流程强制 | ⚠️ 待做 |

**新增 L5 建议实现**（简单脚本，node 零依赖）：
```js
// scripts/check-secrets.mjs — 提交前扫描敏感信息
const DENY = [/api[_-]?key\s*[:=]\s*['"][A-Za-z0-9]{16,}/i, /password\s*[:=]/i, /sk-[A-Za-z0-9]{16,}/]
const FILES = ['llm.config.json', '.env', '*.local.json']
// 扫描 git 暂存区文件，命中即 exit 1 阻止提交
```

## 8. 度量与复盘

### 8.1 指标（周维度统计，不考核个人，只考核机制）

| 指标 | 定义 | 健康线 |
|------|------|--------|
| 审查覆盖率 | 已审查 PR / 总 PR | ≥ 90%（紧急修复事后补审也计入） |
| 平均首轮反馈时长 | 提交 → 首条评论 | ≤ 24h |
| 每 PR 🔴 数 | 平均 | ≤ 1（>1 说明设计/自检环节弱） |
| 案例库增量 | 本周新增的"踩坑→案例" | 每周 ≥ 1 |
| 线上缺陷回流量 | 上线后 2 周内因审查遗漏导致的 bug | 目标 0 |

### 8.2 复盘节奏

- **周会 5 分钟**：过一遍本周 🔴 问题清单 → 挑 1 个最典型的进案例库（§9）
- **月会 15 分钟**：指标回顾 → 流程哪里卡 → 迭代规范版本号
- **季度**：审查记录表归档，提炼"团队高频错误 TOP10"更新 §3 清单

## 9. 团队真实案例库（踩坑即教材）

> 这些是团队自己踩过的坑，审查时**优先检查对应检查项**。每条都标注了"应在哪一步被拦下"。

### 案例 1：路径穿越泄露 API 密钥 🔴 安全（S1/S2）
- **现象**：`/file/llm.config.json` 可直接下载，LLM API key 暴露
- **根因**：静态文件路由未做敏感文件过滤
- **教训**：**所有对外提供文件的入口必须过黑名单**；配置类文件一律禁止静态路由
- **审查拦截点**：§3.2 S2 —— 这条漏审=上线即事故

### 案例 2：ESM 命名空间对象冻结 🔴 运行时（C4/M7）
- **现象**：编辑器"点击没反应"，报错 `Cannot add property applyProps, object is not extensible`
- **根因**：`window.__editor` 是 `import * as` 命名空间（冻结对象），动态加属性抛 TypeError
- **教训**：**ESM 命名空间对象不可扩展**——回调函数必须导出，不能运行时赋值
- **审查拦截点**：§3.1 C4（运行时错误）+ §3.3 M7（ESM 语义边界）

### 案例 3：DOM 注入顺序与渲染顺序不一致 🔴 交互错位（C1/T3）
- **现象**：编辑器"拖 A 动 B"，点击全部错位
- **根因**：data-id 按解析顺序注入，渲染按布局顺序输出——布局重排后两者不一致
- **教训**：**浏览器端注入顺序必须与渲染输出顺序同源**；SVG 交互标记要标在"覆盖全部可点击子元素的祖先"上（文字与形状是兄弟节点）
- **审查拦截点**：§3.1 C1（逻辑正确性）——这类 bug 只能靠审查者问一句"注入顺序和渲染顺序一致吗？"

### 案例 4：模拟事件假阳性 🔴 测试盲区（T3）
- **现象**：自检 9/9 全绿，但用户真实鼠标点击无反应
- **根因**：`dispatchEvent` 直接派发在目标元素上，绕过了真实点击的命中链路
- **教训**：**验证交互必须用真实事件**（CDP Input.dispatchMouseEvent）；模拟事件只能做单元级验证
- **审查拦截点**：§3.5 T3 —— 看到"自检通过"先问"这是模拟的还是真实的？"

### 案例 5：事件处理器内全量重渲染 🔴 交互失效（P3/C7）
- **现象**：编辑器"有高亮但拖不动"
- **根因**：pointerdown 里 selectNode → 全量 innerHTML 重建 → 拖拽引用的旧 DOM 失效
- **教训**：**拖动类交互必须"DOM 直改 + 松手提交"**，事件处理器内禁止全量重渲染
- **审查拦截点**：§3.4 P3（前端性能/交互）+ §3.1 C7（引用失效）

### 案例 6：关键字前缀误判 🔴 逻辑回归（C2/M7）
- **现象**：节点 id `END` 被 `startsWith('end')` 当成 subgraph 结束关键字，形状丢失
- **根因**：前缀匹配代替精确匹配
- **教训**：**解析器关键字匹配必须精确**（`===` 而不是 `startsWith`）；修完必须加回归用例
- **审查拦截点**：§3.1 C2 + §3.5 T2（回归测试）

### 案例 7：环境差异假故障 🟡 排查误导（T4/C6）
- **现象**：测试用 `/tmp` 路径，Windows 下 bash 视角与 Node 视角不一致，误判失败
- **根因**：跨平台路径/管道行为差异（process substitution、emoji 编码、管道时序）
- **教训**：**测试与调试不要在环境相关路径上做假设**；Windows 下避免 process substitution，管道输出用文件落盘验证
- **审查拦截点**：§3.5 T4（测试数据环境无关性）
